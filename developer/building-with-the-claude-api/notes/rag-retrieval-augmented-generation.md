## Objective

Understand the RAG pattern, its components, and how to build a full RAG pipeline for querying large documents.

---

## What RAG Is

A technique for querying large documents (100–1000+ pages) using language models without hitting context limits.

### The Problem with Direct Approach

Placing the entire document into a prompt:
- Hard token limits
- Decreased effectiveness with longer prompts
- Higher costs and slower processing

### The RAG Approach

1. Break document into small chunks
2. For user questions, find the most relevant chunks
3. Include only those chunks in the prompt

**Benefits:** Model focuses on relevant content, scales to multiple documents, smaller prompts, lower cost, faster processing
**Downsides:** More complexity, requires preprocessing, needs a search mechanism, no guarantee chunks contain complete context

---

## Text Chunking Strategies

Chunking quality directly impacts RAG performance — poor chunking retrieves irrelevant context.

| Strategy | How It Works | Pros | Cons |
|---|---|---|---|
| **Size-based** | Equal-length character strings | Easy to implement, common in production | Cut-off words, lacks context |
| **Structure-based** | Split on headers, paragraphs, sections | Best for structured docs (markdown, HTML) | Requires guaranteed formatting |
| **Semantic-based** | NLP groups related sentences | Most accurate | Most complex |

**Overlap strategy for size-based:** Include characters from neighboring chunks to preserve context — creates duplication but improves chunk meaning.

> Rule: No universal best method — depends on document structure and use case.

## Text Embeddings

Numerical representation of text meaning generated by embedding models.

- **Embedding model:** Takes text input, outputs a long list of numbers (range –1 to +1)
- **Each number:** Scores an unknown quality/feature of the text
- **Semantic search:** Matches user queries to relevant chunks by comparing embeddings rather than keywords

**Recommended provider:** Voyage AI (Anthropic-recommended) — free to start, easy SDK integration.

---

## The Full RAG Flow (7 Steps)

1. **Text chunking** — split source documents into pieces
2. **Generate embeddings** — convert chunks to numerical vectors
3. **Normalization** — scale vector magnitudes to 1.0 (handled by embedding APIs)
4. **Vector database storage** — store embeddings in a specialized database
5. **Query processing** — convert user question into an embedding using the same model
6. **Similarity search** — find most similar stored embeddings using cosine similarity
7. **Prompt assembly** — combine user question with retrieved chunks, send to LLM

### Key Math

- **Cosine similarity:** cosine of angle between vectors; closer to 1 = more similar
- **Cosine distance:** 1 minus cosine similarity; closer to 0 = higher similarity

## BM25 Lexical Search

A lexical search algorithm that complements semantic search in a **hybrid search** approach.

**Problem with semantic search alone:** Can miss exact term matches even when specific terms appear frequently.

**BM25 algorithm:**
1. Tokenize query into separate terms
2. Count frequency of each term across all chunks
3. Assign importance based on frequency (rare terms = higher importance)
4. Rank chunks by weighted term frequency

**Hybrid search:** Run semantic + BM25 in parallel, merge results — gets semantic understanding AND exact term matching.

---

## Multi-Index RAG Pipeline

Combines a **Vector Index** (semantic) and **BM25 Index** (lexical) using **Reciprocal Rank Fusion** to merge results.

**RRF formula:**
```
RRF_score = sum of (1 / (rank + 1)) across all search methods
```

Documents ranked highest across both methods float to the top.

---

## Reranking

A post-processing step that uses an LLM to reorder search results by relevance after initial retrieval.

**Process:** Vector + BM25 search → merge → pass to LLM with relevance ranking prompt → reordered results

**Trade-offs:** Better accuracy, increased latency, additional API cost.

**Best for:** Queries where initial retrieval misses nuanced intent (e.g., "ENG team" vs "engineering team").

---

## Contextual Retrieval

Adds context to document chunks **before** embedding to improve retrieval accuracy.

**Problem:** Individual chunks lose context from the original document when split.

**Solution:**
1. Take chunk + original source document
2. Send to Claude — generate brief situating context
3. Join context + original chunk = "contextualized chunk"
4. Use contextualized chunk in vector/BM25 indexes

**Large document handling:** Include starter chunks (for summary) + chunks immediately before target chunk. Skip middle chunks.

---

## Key Takeaways

- RAG trades simplicity for scalability — the right choice for large or multi-document knowledge bases
- Hybrid search (semantic + BM25) consistently outperforms either approach alone
- Reranking is a quality multiplier — use when initial retrieval isn't accurate enough
- Contextual retrieval significantly improves chunk quality before they ever hit the index
