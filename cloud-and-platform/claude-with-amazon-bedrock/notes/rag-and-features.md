## Retrieval Augmented Generation (RAG)

### The Problem

Querying large documents (100–1000+ pages) with Claude hits token limits and degrades performance.

### The RAG Approach

1. Break document into small chunks
2. For user questions, find the most relevant chunks
3. Include only those chunks in the prompt

**Benefits:** Focused context, scales to large/multiple documents, smaller prompts = faster and cheaper.

### Text Chunking Strategies

| Strategy | Pros | Cons |
|---|---|---|
| **Size-based** | Easiest to implement, most common | Cuts off words, lacks context |
| **Structure-based** | Well-formed, contextual sections | Requires structured documents |
| **Semantic-based** | Most accurate | Most complex |

**Overlap strategy for size-based:** Include characters from neighboring chunks — creates duplication but preserves context.

**Default fallback:** Character-based chunking — works across all document types.

### Text Embeddings

Numerical representation of meaning generated by embedding models (e.g., Titan Embed Text V2 on Bedrock).

- Output: list of ~1024 numbers (range –1 to +1)
- Enable semantic search — matches by meaning, not keywords

### The Full RAG Flow (7 Steps)

1. Text chunking
2. Generate embeddings
3. Normalization (auto-handled by embedding APIs)
4. Vector database storage
5. Query processing (embed user question)
6. Similarity search (cosine similarity)
7. Prompt assembly + LLM generation

**Cosine distance:** 1 minus cosine similarity — closer to 0 = higher similarity.

### Hybrid Search (BM25 + Semantic)

**BM25** = lexical search algorithm that weights rare terms higher than common terms. Complements semantic search by handling exact keyword matches.

**Reciprocal Rank Fusion (RRF):** Merges results from both search methods.
```
RRF_score = sum of (1 / (1 + rank)) for each method
```

### Reranking

Post-processing step using LLM to reorder search results by relevance after initial retrieval. Increases accuracy, increases latency — use when initial retrieval isn't accurate enough.

### Contextual Retrieval

Add LLM-generated context to each chunk before embedding — chunks retain connection to overall document structure. Improves retrieval accuracy for complex, interconnected documents.

## Features of Claude

### Extended Thinking

Allows Claude to reason before generating a final response.

- **Thinking budget:** minimum 1024 tokens; `max_tokens` must exceed budget
- **Cost:** thinking tokens are charged
- **When to use:** after prompt optimization fails — always eval-driven, not assumption-based
- **Redacted thinking blocks:** encrypted content flagged by safety systems — provided for conversation continuity

### Image Support

- Max 20 images per request on Bedrock
- Images consume tokens based on pixel dimensions
- **Critical:** prompt engineering is the key to accuracy — simple prompts consistently produce poor results
- Effective techniques: step-by-step analysis instructions, one-shot/multi-shot examples

### Prompt Caching

Stores Claude's processing work in a temporary cache (5-minute TTL) to avoid reprocessing identical content.

**Implementation:**
```python
# System prompt caching
{"type": "text", "text": system_prompt, "cache_control": {"type": "default"}}

# Tools caching — append cache_point to tools list
```

**Usage monitoring:**
- `cache_write_input_tokens` — tokens stored to cache
- `cache_read_input_tokens` — tokens retrieved from cache

**Requirements:**
- Minimum 1024 tokens before cache point
- Content before cache point must be exactly identical between requests
- Any change invalidates the cache

## Model Context Protocol (MCP)

### What MCP Is

A communication layer providing Claude with context and tools without requiring developers to write tool schemas and functions manually. MCP servers shift integration burden to server maintainers.

### The Three Primitives

| Primitive | Controlled By | Purpose |
|---|---|---|
| **Tools** | Model (Claude decides) | Add capabilities to Claude |
| **Resources** | Application (app decides) | Provide data to UI or prompts |
| **Prompts** | User (triggered by action) | Predefined workflows |

### Key Functions

```python
list_tools()              # await self.session.list_tools()
call_tool(name, input)    # await self.session.call_tool(...)
list_prompts()            # await self.session.list_prompts()
get_prompt(name, args)    # await self.session.get_prompt(...)
```

**Bedrock-specific note:** MCP tool definitions must be converted to Bedrock format via `to_bedrock_tools()` function — schemas differ from Anthropic API format.

## Key Takeaways

- RAG trades complexity for scalability — the right choice for large document knowledge bases
- Hybrid search (semantic + BM25) consistently outperforms either approach alone
- Contextual retrieval + reranking are the two highest-leverage RAG quality improvements
- Extended thinking is a last resort after prompt optimization — always eval-driven
- Prompt caching has 5-minute TTL on Bedrock — design breakpoints around stable, repeated content
- MCP tool schemas require Bedrock-specific conversion — a key difference from the Anthropic API
